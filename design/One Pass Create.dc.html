Feature design · one-pass create · #1390

Adding a piece in one pass

The core half shipped: AddPieceInFull validates the piece, every staged exercise and the chart before it mutates anything, and writes one batch. This is the surface. Constraint set: specs/one-pass-create.md; ruling T21. The minimal form stays minimal — two collapsed rows below the existing fields, nothing written until Add, one primary on the screen.

Everything above the fold is unchanged and is not redrawn here — ScanPageEntry, the kind picker and the field cards are canonical in Design System · Screens · Add piece; the words come from the piece's Related exercises card. The frames below start at the foot of the form, where the new rows live.

F1 · the collapsed state (ask 1 & 3)
  • Nouns win. “Chord chart” and “Related exercises” — the same words the detail card wears, so one thing has one name across two surfaces. Verb-led rows lose on a harder point than tone: “Add chord chart” puts a second Add on a screen whose only primary is Add.
  • Silent when collapsed. No caption, no count, no “optional”. A piece with neither pays two rows, nothing more.
  • The caption the tone doc allows is spent on expansion — one sentence, at the decision point, once (F3). Collapsed, the row is a promise the app can keep in one tap; it needs no sales line.
  • Both rows sit last, below Tags. The fields say what the piece is; the rows carry what comes with it. Ordering them next to ScanPageEntry was tempting — a page can fill the chart — but proximity is the wrong instrument for that: the read mark is (F5). Sitting last also leaves ItemFormScaffold's existing order untouched, so the edit path is unchanged.
  • Chevrons differ on purpose: right on the chart (it opens the existing sheet), down on exercises (it expands in place). Spec decision 5 keeps one chart editor; cloning it inline would make two.

F2 · staged, nothing written yet (ask 2)
  • The chart shows as the text you typed — monospaced, three lines, then a fade, with Edit where the detail card puts it. Not a bar count and not a bar grid: both claim a parse this form has not run. The chart is parsed when Add is pressed, so anything that looks parsed here would be a promise the screen can't keep.
  • Removal is a per-row minus, the same control the detail card's edit mode uses — no Edit mode of its own. A three-row draft with no reorder doesn't earn a mode.
  • Written and chosen rows look identical, and that's the ruling: until Add, neither exists, and removing either writes nothing. A “from your library” badge would imply the row already had a life the form has to respect.
  • The two actions become the detail card's populated footer verbatim — Create an exercise · Choose one. No filled bar anywhere in the sections: Add stays the only primary.
  • Answers spec open question 2: a rejected create leaves this exactly as drawn. The draft is shell state; the banner appears above, the rows stay, and nothing was written to clean up.

F3 · two actions, no competing buttons (ask 2)
  • The detail card's empty state gives the sentence and both actions; this borrows all three verbatim, minus one thing: the BrandBarButton. On the piece there is one obvious next step, so the filled indigo bar is right; here it would out-shout Add. Both actions become plain accent rows, divided by a hairline — equal weight, and the order carries the recommendation.
  • “Create an exercise” opens a small sheet that returns a draft rather than sending an event (F4). “Choose one from the library” is LinkedItemPickerSheet unchanged — it links existing exercises only, which is exactly its job here.
  • No ellipsis on either, and neither is a mode: the section stays open behind the sheet, so coming back is landing where you were.

F4 · DraftExerciseSheet
  • Three fields — title, key, bpm — because a ScaffoldEntry::New only needs a valid title and the two things a musician says out loud in the same breath. Notes, tags and steps belong to the exercise's own screen, after it exists.
  • Done, not Add: the word Add is reserved for the create that writes. One sentence says where the row goes, at the only point where “nothing is written yet” could surprise someone.
  • Deliberately not LibraryAddScreen(relatedToPieceId:): that path mints and links immediately, which on the create path would write an exercise for a piece that doesn't exist.

F5 · the page can fill the chart (ask 3)
  • The chart row arrives already expanded and marked, wearing FieldMark unchanged — same icon, same words, same dimmed variant for a weak read. This is the whole shell-side cost of phase D: ReadField.chart.
  • Note the composer's mark is the dimmed one: read, but not clearly. Contrast never carries it alone — the hint is spoken.
  • Editing the chart text takes the mark off on the first keystroke, exactly as the fields do. A second scan replaces what the first wrote.
  • Frames F1–F4 are scrolled to the foot; this one is the top of the same form, showing that the scan entry did not move. A page filling four things across two ends of the form is an argument for marks, not for regrouping.

F6 · the banner says it once (ask 4)
  • The banner keeps the sentence; the row carries the pointer. ItemFormScaffold's banner behaviour is unchanged — it holds the core's own per-token message and stays on screen. The section expands, takes the danger hairline and marks the offending token in place, and repeats no words. One message, two ends of the same thread.
  • Pressing Add scrolls the marked section into view, so the pointer is never off-screen while the banner accuses it.
  • last_error is a single slot, so exactly one row is ever marked. Here the staged exercise is fine; if it weren't, its title would have surfaced first and the chart would sit unmarked — the core stops at the first failure, and the screen must not invent a second verdict.
  • Nothing was written. The chart text, both staged rows and every field are still here — the draft is shell state and the create was refused whole.
  • Live per-bar feedback while typing stays out (#1387). The mark appears on Add and clears when the text changes.

F7 · only one error surfaces
  • The same create as F6, plus a titleless row. The core validates exercises before it parses the chart, so the title wins — and the chart above holds the same bad bar with no mark on it. That is correct, not a miss: the app only says what the core actually decided.
  • The offending row is skinned, not the whole section: within a list, the pointer has to be the row. “Untitled” is the row's own placeholder, in danger ink.
  • Fixing the title and pressing Add again surfaces the bar — the second press is where the chart's turn comes. Two problems, two presses, and no screen that pretends to know both.

F9 · full at large type (ask 5)
  • The two-up footer stacks above .accessibilityMedium — side by side, “Create an exercise” would break onto three lines in half a phone's width. Stacked, they are the same two rows as the empty state, which is a smaller vocabulary to learn, not a bigger one.
  • The staged chart clamps to two lines at these sizes, still monospaced and still verbatim: it is a reassurance that the paste landed, and one section label plus one bar line does that.
  • Remove keeps a 44pt target throughout, and titles wrap rather than shrink — minimumScaleFactor is for the bar grid on the detail card, not for a musician's own words.
  • Everything else is scroll, and that is the right answer: the form is already the app's longest scroll, and a piece that carries both is the case the user asked for.
5 · What this asks of the system

Four named parts, no new tokens

New components
  • FormSectionRow — a noun, a chevron, and a card surface: the collapsed section inside a form. One flag for whether it opens a sheet or expands in place, one for the error skin.
  • StagedChartCard — header, Edit, and the verbatim monospace clamp with its fade; carries the parse mark and FieldMark.
  • DraftItemRow — an unsaved item row with a remove control. The type bar, title and meta of LinkedExerciseRow, minus the score ring: a draft has no history to show.
  • DraftExerciseSheet — returns a ScaffoldEntry::New instead of sending an event.
Reused unchanged
  • ItemFormScaffold — the two sections append below Tags; existing order and the banner's behaviour untouched, so the edit path does not change.
  • ScanPageEntry, FieldMark, LinkedItemPickerSheet — as they are.
  • ChordChartEditSheet — gains the text-returning mode spec decision 5 already allows; not cloned.
  • ItemFormModel.ReadField — one case, chart.
Theme.swift
  • No new colour, spacing or radius tokens. Every surface here is cardFill + hairline, the inner chart block is paperTop + divider at IntradaRadius.badge, and the error skin is danger at 10% — the same tint the chart sheet already uses.
  • One candidate: the monospace chart face is now written in three places (.body in the sheet, .footnote here, and the detail grid). If this design wins, that earns IntradaFont.chart rather than a fourth literal.
Still open
  • The edit path gets neither section (spec open question 1 stays held). If the create form teaches these words, the piece screen is where a chart gets changed — worth a second look after the snapshots.
  • Online mode: the event refuses when a chart or an exercise is present. The refusal message lands in the banner like any other, and neither section is marked — nothing on the screen is at fault. Worth confirming that reads as an app state rather than a mistake.
  • Two frames of the spec's snapshot list are drawn here (F1 collapsed, F2 staged); F6 is the third worth pinning.
